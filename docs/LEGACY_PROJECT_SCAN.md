# Legacy predictor scan — October 9, 2026

Read-only source and CSV inspection of `/Users/andry/Downloads/NHL_Project`, `/Users/andry/Downloads/untitled folder/nba`, and a limited cross-check of its sibling `nhl`. No legacy program executed, dependencies installed, model pickle/joblib deserialized, credentials opened, or source changed. This is a focused audit, not an exhaustive security or performance audit.

## Confirmed findings

1. **Weight adjustment is disconnected from prediction.** In all three copies, `models/advanced_prediction_system.py:56` constructs local fixed weights sports=.3, combined=.3, vedic=.4. `adjust_weights` at line 90 writes `self.weights`, which that prediction path never reads; `get_model_weights` also returns constants. A targeted source search in the NBA tree found only the method definition, no caller. This path does not provide automatic learned combination weights. It does not prove every other model in the folder is static.
2. **NBA evaluator is incompatible with its current CSV.** `untitled folder/nba/evaluate_model_performance.py:18` reads `data/nba_games_data.csv`, then expects `Date`, `PTS`, and `PTS.1`. The actual 19,466-row CSV has `date,visitor_team,home_team,visitor_score,home_score,season`. As shipped, execution would fail at `data['Date']`. Even if corrected, line 65 uses a shuffled split, not a chronological prospective evaluation; its before/after runs change the evaluation population, so their difference is not a same-test-set improvement estimate.
3. **Head-to-head margin has a double sign reversal.** Shared `enhanced_features.py:64` flips margin when the current home team was previously away, although the preceding home_points/away_points variables already orient scores to that team. Example: a previous 110–100 away win should contribute +10; this code contributes -10. Identical file hashes in all three copies.
4. **Synthetic generator has target leakage, but its presence does not establish all saved training data is synthetic.** `NHL_Project/generate_historical_data.py:118` computes rolling target sums without shifting, including each game's own outcome. `train_model.py` consumes this output path and keeps these fields. The currently saved CSV has 3,865 rows with named NBA teams and no `Team_` rows (generator uses Team_0 etc.); other scripts overwrite the same path. Its exact provenance is unresolved. Do not claim the existing saved models definitely trained on generated games without tracing their artifacts.
5. **Headline evidence is duplicated and not a verified live ledger.** `predictions/evaluation_results.csv` is byte-identical in all three copies: 155/237 correct (65.4%), versus 141/237 home wins (59.5%); it predicts home 165/237 times (69.6%). Columns have game date but no forecast creation timestamp or training cutoff. Its writer `evaluate_predictions.py` loads one existing model and evaluates past games: it does filter feature inputs to earlier game dates, but does not establish that the saved model was trained before those games. This is not three independent evaluations or a verified prospective result.
6. **The perfect record is only 20 rows.** `detailed_predictions.csv` has 20/20 correct in the inspected NHL_Project and NBA copies; the threshold summary repeats those 20 games. No independently verified provenance or selection process was established. Do not equate it to a reliable 100% system.
7. **NHL_Project's named NHL predictor is a stub.** `models/nhl_predictor.py` has pass bodies for train_models and predict_game. This finding is specific to that class, not proof every NHL-named file is empty.

## Useful material to retain

- Thirty NBA arena coordinate entries in `arena_locations.json`: a starting point for schedule-derived travel features, after checking dates, neutral venues, relocations and naming. Coordinates alone do not encode time zones or altitude. No predictive benefit measured here.
- Existing past-date-filtered recency/form and rest calculations in `enhanced_features.py`: useful hypotheses and reference formulas, with the sign bug fixed. Current app already has rest/back-to-back features; avoid duplicating them.
- `analyze_predictions.py` explains picks through recent form, margins and matchups. This is a useful product presentation idea if tied to actual model inputs, not post-hoc assertions of confidence.
- Existing result CSVs can support a provenance audit, but are not suitable for a claims page until timestamps, training cutoffs and selection are established.

## Recommendation

Keep these folders as archives. Port neither saved models nor accuracy claims blindly. First complete current recovery and safe-transition work. Then isolate a travel/schedule experiment with chronological evaluation and a genuinely unused final test; compare with existing features and models on the same games. The scan establishes concrete legacy defects, not that the current app has better predictive accuracy.
